# Дом рядом

**Дом рядом — помощь у порога.**

Сервис обращений жителей многоквартирных домов. Основной сценарий работает в чат-боте MAX: житель выбирает проблему и дом, описывает ситуацию, получает номер, ответственного и следующий шаг. Диспетчер обрабатывает заявки в закрытой веб-панели. Локальная веб-форма доступна отдельно по `/app`.

## Проблема, аудитория и эффект

Приоритетный пользователь — житель дома, который заметил неисправность общего имущества (например, протечку в подъезде) и хочет понять, кому сообщить о ней и зарегистрировано ли обращение. Второй участник — диспетчер управляющей организации, которому нужна единая очередь и история решений. Гипотеза команды: единый короткий сценарий в MAX уменьшит число шагов до регистрации обращения и неопределённость для жителя. Это гипотеза для проверки на пилоте, а не подтверждённый результат исследования.

В MVP результат для жителя — номер заявки, ответственный, следующий шаг, доступ к статусу и уведомление об изменении. Для диспетчера — список, фильтры, изменение статуса и история. Предлагаемые метрики пилота: медианное время от первого сообщения до созданной заявки; доля начатых диалогов, завершившихся заявкой; доля заявок с изменением статуса; время до первой реакции диспетчера; доля жителей, повторно спрашивающих о статусе вручную. Начальные значения и целевые пороги следует определить с пилотной УК, а не придумывать для демонстрации.

### Пилот и тиражирование

Первый пилот — одна согласившаяся управляющая организация и один-два её дома. До запуска нужно заменить вымышленные записи домов и контакты на проверенный справочник УК, согласовать маршрутизацию категорий и порядок обработки обращений, назначить диспетчера и канал поддержки. Процесс остаётся тем же при переходе к другой УК: MAX → заявка → работа диспетчера → обратная связь. Меняются дома, контакты, зоны ответственности, правила обработки, роли и интеграции. Для нескольких организаций потребуется разграничение данных по организации; для нескольких экземпляров бота — координация одного владельца polling и последовательности событий каждого диалога.

## Что уже работает

**Жителю в MAX:**

- диалог создания заявки через `/start` или `/new`;
- `/my` — последние 10 своих обращений;
- `/status REQ-000001` — текущий статус своей заявки;
- сообщение при смене статуса диспетчером, включая комментарий;
- `/cancel` — отмена текущего диалога.

**Жителю в локальной веб-форме:**

- выбор дома и категории проблемы;
- описание ситуации с проверкой заполненных данных;
- определение ответственной службы и подсказка о дальнейших действиях;
- копирование готового текста обращения;
- создание заявки с автоматическим номером вида `REQ-000001`;
- адаптивный интерфейс для телефона.

**Диспетчеру (панель закрыта паролем):**

- список заявок с поиском по номеру и описанию;
- фильтр по статусу, сортировка по номеру и дате, переключение порядка;
- свободная смена статуса без жёсткой лестницы переходов;
- обязательная причина только при отказе;
- история смены статусов с автором, временем и сохранённой причиной;
- поиск и фильтры сохраняются в адресе страницы, поэтому ссылку можно переслать коллеге.

**Хранение:**

- PostgreSQL, заявки переживают перезапуск сервера;
- журнал смены статусов пишется в той же транзакции, что и сам статус;
- миграции 001–007 накатываются на пустой базе; таблицы для MAX создаются также при старте приложения на существующем томе;
- незавершённый диалог, входящие события, курсор polling и очередь уведомлений хранятся в PostgreSQL и переживают перезапуск;
- повторное сообщение MAX с тем же `mid` не создаёт вторую заявку.

## Требования

- Docker и Docker Compose — проще всего;
- либо Go 1.27+ и PostgreSQL, если запускать без Docker.

## Архитектура и состав

Один Go-процесс обслуживает HTTP API, локальную форму `/app`, панель диспетчера `/admin` и бот MAX. PostgreSQL хранит дома, организации, заявки, историю статусов, сессии диалогов, входящие события с курсором и очередь уведомлений. Бот получает события MAX через исходящий Long Polling: пачка событий и новый курсор фиксируются одной транзакцией, затем отдельный обработчик читает inbox по порядку и повторяет сбойные события с задержкой. Сообщение с уже использованным `mid` возвращает номер прежней заявки; уникальный индекс защищает от конкурентной вставки. Управляющие организации не подключены к реальной системе — использованы демонстрационные записи.

| Компонент | Роль | Адрес/порт |
|---|---|---|
| Go-приложение | API, интерфейсы, бот MAX | `http://localhost:8080` (`PORT`, по умолчанию 8080) |
| PostgreSQL 16 | постоянное хранение | `db:5432` внутри Docker, наружу не опубликован |
| MAX API | приём событий и отправка сообщений | исходящий HTTPS к `platform-api2.max.ru` |

### Зависимости

Библиотеки Go зафиксированы в `go.mod` и `go.sum` (основная внешняя библиотека — `pgx/v5` для PostgreSQL); фронтенд — обычные HTML/CSS/JavaScript без отдельной сборки. Для запуска через Docker локальные Go и PostgreSQL не нужны.

### Переменные окружения

| Переменная | Назначение |
|---|---|
| `POSTGRES_PASSWORD` | пароль базы в Compose; задайте свой в `.env` |
| `DATABASE_URL` | строка подключения; Compose формирует её для сервиса `db` |
| `AUTH_SECRET` | секрет подписи сессий, не менее 32 символов |
| `DISPATCHER_LOGIN` | логин первого диспетчера, по умолчанию `dispatcher` |
| `DISPATCHER_PASSWORD` | необязателен; если пуст, пароль генерируется при первом запуске и один раз выводится в лог |
| `MAX_BOT_TOKEN` | токен бота MAX; если пуст, бот отключён |
| `MAX_API_URL` | необязательный адрес API MAX для тестов; обычно не задавать |
| `COOKIE_SECURE` | `true` только при доступе через HTTPS; для `localhost` — `false` |
| `PORT` | HTTP-порт Go-приложения, по умолчанию 8080; при смене обновите проброс порта Compose |

`.env.example` содержит только образцы значений. Рабочий `.env` исключён из Git. Токен MAX — внешний секрет, сам сервис MAX внутри Docker не воспроизводится; для проверки бота нужны действующий токен и исходящий доступ к MAX API.

## Запуск через Docker Compose

```bash
git clone https://github.com/jadoreblessed/dom-ryadom.git
cd dom-ryadom
cp .env.example .env
```

В `.env` задайте `POSTGRES_PASSWORD`, `AUTH_SECRET` (не менее 32 символов) и выданный токен `MAX_BOT_TOKEN`. Сгенерируйте ключ подписи сессий:

```bash
openssl rand -hex 32
```

Потом выполните одну команду для запуска приложения и PostgreSQL:

```bash
docker compose up -d --build
```

Чтобы посмотреть лог бота и пароль первого диспетчера: `docker compose logs app`.

Без токена HTTP-часть работает, но бот отключён. MAX получает сообщения через исходящие запросы Long Polling: публичный адрес для **бота** не требуется. Запускайте только один экземпляр приложения с данным токеном.

При первом запуске пароль диспетчера **генерируется случайно и печатается в лог один раз**:

```text
создан диспетчер "dispatcher", пароль сгенерирован: <ваш пароль>
```

Сохраните его: в базе лежит только хеш, восстановить пароль нельзя. Узнать его позже можно только удалив учётную запись и перезапустив приложение.

| Адрес | Кто видит |
|---|---|
| `http://localhost:8080/app` | форма подачи заявки жителем |
| `http://localhost:8080/login` | вход диспетчера |
| `http://localhost:8080/admin` | панель заявок, требует входа |
| `http://localhost:8080/health` | проверка работы сервера |

### Пароль из `.env`

Переменной `DISPATCHER_PASSWORD` в `.env` нет намеренно. Если её задать, приложение возьмёт пароль оттуда, но он перестанет действовать при пересоздании базы. Заглушка вида `change-me` опаснее её отсутствия: она одинаково подходит всем, кто её видел, а `.env` рано или поздно уезжает в репозиторий или в архив.

`AUTH_SECRET` обязателен и не короче 32 символов. С более коротким приложение не стартует: такую подпись можно подобрать перебором и выпустить сессию от чужого имени.

Нужны переменные `DATABASE_URL`, `DISPATCHER_LOGIN`, `AUTH_SECRET`, `PORT` и `MAX_BOT_TOKEN` для бота. Миграции в этом режиме накатываются вручную, по порядку:

## Статусы заявок

Четыре статуса, `GET /statuses` отдаёт их список и отдельно закрытые:

| Статус | Закрытый | Смысл |
|---|---|---|
| `Новая` | нет | заявка принята, диспетчер ещё не взял |
| `В работе` | нет | назначена ответственному |
| `Выполнена` | да | работа закончена |
| `Отклонена` | да | отказ, причина обязательна |

Заявку можно вернуть в работу из любого состояния — в том числе из закрытого, по кнопке «Изменить статус». Единственный запрещённый переход — в тот же статус, он отклоняется с `400` и текстом «Статус заявки не изменился»: молчаливый отказ трудно понять.

Причина обязательна только для `Отклонена` и сохраняется в журнале вместе со сменой статуса, поэтому не теряется, когда следующим действием статус меняют снова.

## Доступ к данным

Закрыты и требуют сессии диспетчера:

- `GET /admin`;
- `GET /requests` — список всех заявок всех жителей;
- `GET /requests/{number}`;
- `GET /requests/{number}/history`;
- `PATCH /requests/{number}/status`;
- `GET /auth/me`.

Открыты всем, включая подачу заявки: `/app`, `/login`, `/statuses`, `/categories`, `/buildings`, `/requests/preview`, `POST /requests`, `/health`.

Пароли хранятся как `PBKDF2-HMAC-SHA256`, 600 000 итераций, соль на пользователя, число итераций записано внутрь хеша. Сессия — подписанная cookie `HttpOnly` и `SameSite=Lax` на 12 часов. Неверный логин и неверный пароль дают одинаковый ответ и одинаковое время ответа, чтобы по времени нельзя было перебирать логины. Учётная запись создаётся один раз и не перетирается при каждом перезапуске.

```json
{ "status": "Отклонена", "comment": "Не входит в зону ответственности" }
```

### История заявки

```json
[
  {
    "from_status": "Новая",
    "to_status": "В работе",
    "changed_by": "dispatcher",
    "comment": "",
    "changed_at": "2026-09-28T19:30:49Z"
  }
]
```

`changed_by` — логин вошедшего диспетчера, а у первой записи всегда `resident`.

### Данные для локальной проверки

`002_seed.sql` создаёт два вымышленных дома: `house-1` — «ул. Лесная, д. 5», УК «Тестовая УК №1»; `house-2` — «ул. Садовая, д. 10», УК «Тестовая УК №2». Это демонстрационные данные, не сведения ГИС ЖКХ. Категории и правила определения ответственного заданы в `routing.go`; заявка связывается с выбранным домом, а не принимает адрес от пользователя как источник истины. В `requests` хранится текущий статус, в `request_status_history` — все изменения. Связь с MAX хранится как числовой ID пользователя, токен остаётся только в `.env`.

Для воспроизводимой проверки выберите `house-1`, категорию «Протечка» и описание «Течёт труба на первом этаже». Ожидается новая заявка `REQ-...`, ответственный «Аварийно-диспетчерская служба» и совет связаться с аварийно-диспетчерской службой. Номер зависит от уже созданных заявок. Данные не исчезают при остановке контейнеров; удаление тома `postgres_data` уничтожит их.

## Проверка полного сценария

1. Выполните `docker compose up -d --build`; откройте `http://localhost:8080/health` — ответ `{"status":"ok"}`.
2. Откройте чат бота MAX и отправьте `/new`. Выберите категорию, дом, отправьте описание. Бот вернёт номер вида `REQ-000001`, ответственного и следующий шаг.
3. Отправьте `/my` и `/status REQ-000001`: бот покажет только заявки этого MAX-пользователя.
4. Откройте `http://localhost:8080/login`, войдите под `DISPATCHER_LOGIN` и паролем из первых логов приложения. В панели откройте заявку и смените статус.
5. В чате MAX появится уведомление. Если API MAX временно недоступен, сообщение останется в очереди PostgreSQL и будет отправлено повторно. У заявки, созданной через `/app`, MAX-получателя нет.

Ожидаемое поведение при ошибках: неизвестная категория или пустое описание в форме дают HTTP 400 с полем `error`; закрытые маршруты диспетчера без входа дают HTTP 401; неизвестный номер в `/status` не раскрывает чужую заявку; отказ без причины отклоняется. После `docker compose down` и повторного `up` заявки, история, незавершённый диалог, курсор polling и необработанные события остаются в базе. Если обработка события падает, бот сначала повторяет его, затем переходит к следующему; повтор сообщения создания возвращает прежний номер без второй заявки.

Для остановки: `docker compose down`. Для повторного запуска: `docker compose up -d --build`. Том `postgres_data` хранит заявки и пароль диспетчера; `docker compose down -v` **удаляет все данные**.

## Веб-форма и мини-приложение MAX

`/app` — адаптивная локальная веб-форма. Для подключения именно как мини-приложения MAX в настройках бота нужен публичный HTTPS-адрес этой страницы. `localhost:8080` доступен только на компьютере, где запущен Docker, и в поле URL мини-приложения не подходит. Если команда не размещает веб-часть, поле в настройках MAX оставляют пустым; основной сценарий проверяется через чат-бота.

## Ограничения и дальнейшее развитие

- Дома и управляющие организации в миграции 002 — демонстрационные, реальные справочники потребуют импорта и проверки актуальности.
- Long Polling рассчитан на один экземпляр бота с данным токеном. При нескольких репликах нужно назначить одного владельца polling и согласовать обработку диалогов по пользователю; общая база уже содержит очередь и ключи дедупликации.
- Inbox хранит сбойное событие до успешной обработки, поэтому при постоянной ошибке оно задержит следующие сообщения; требуется мониторинг количества попыток и ручная процедура разбора. Если внешний MAX API уже принял ответ, а процесс не успел зафиксировать успех, текстовый ответ может прийти повторно, хотя заявка останется одна.
- Уведомления стоят в очереди PostgreSQL и повторяются с увеличивающимся интервалом. При сбое между успешной отправкой и отметкой о доставке возможен повтор сообщения; для строгой дедупликации потребуется ключ идемпотентности на внешней стороне.
- Локальная веб-форма не получает идентификатор пользователя MAX; уведомления доступны для заявок, поданных непосредственно через чат.
